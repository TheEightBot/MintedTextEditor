## 2. Root-cause analysis

The editor draws everything itself on an `SKCanvasView`. All typing goes through an invisible 1×1 `KeyboardProxy`. On Android that proxy is backed by `KeyboardCaptureAndroidView` plus a custom `KeyboardInputConnection : BaseInputConnection`. Every symptom traces back to this bridge, as #6 suspected.

### 2.1 What shipped in 0.1.1 (`origin/main`, `KeyboardProxyHandler.cs` `#elif ANDROID`)

| Symptom | Root cause (verified in source) |
|---|---|
| #5 keyboard never appears | Nothing ever calls `InputMethodManager.ShowSoftInput`. `MintedEditorView` calls `_keyboardProxy.Focus()`, which only gives the view focus. It never raises the IME. |
| #5 "can delete but can't type" (hardware/emulator host keyboard) | `OnKeyDown` maps only navigation and edit keys (`Del` → Backspace works). Every printable key falls through to `base.OnKeyDown` and is dropped. |
| #5 / #6-S1 soft-keyboard typing lost or delayed | `KeyboardInputConnection` overrides only `CommitText`, `DeleteSurroundingText` and `SendKeyEvent`. `SetComposingText` (which Gboard on some versions and Samsung always use per keystroke) goes to `BaseInputConnection`'s private `Editable` and never reaches the editor. Text appears only when the IME finally calls `commitText` at a word boundary. That is S1 exactly. The API 35 vs 36 split is consistent with Gboard builds that differ in how eagerly they commit, not with an OS-level difference. |
| #6-S2 MIUI Enter → tofu | MIUI sends Enter as `commitText("\n")`. `CommitText` passes `"\n"` straight to `HandleTextInput` → `InsertTextAction`. A literal U+000A ends up in a run and renders as `.notdef`. Only `KEYCODE_ENTER` mapped to `HandleEnter`. |
| #6-S3 caret keeps blinking | **There is no focus state at all.** `StartBlinkTimer()` runs from `OnHandlerChanged` for the control's whole lifetime, and the caret is drawn whenever `!IsReadOnly` (`MintedEditorView.cs:1139`). Native focus loss on the capture view goes nowhere. `EditorFocusChanged` fires only from the explicit `Focus()`/`Unfocus()` methods, never on tap or native blur. The same code is used on iOS and Windows, so **S3 is cross-platform**, not Android-only. Side effect: the canvas repaints every 100 ms forever, wasting battery even when the editor is idle or off-screen. |

## 3. Approach

1. **Extract the composition logic** (R8) into a platform-neutral `ImeCompositionTracker` in `MintedTextEditor.Core/Input`. It emits abstract ops (`InsertText`, `DeleteBackward(n)`, `DeleteForward(n)`, `Enter`) to a sink. `KeyboardInputConnection` becomes a thin adapter. All of R2/R4/R5/R6 then become unit-testable.
2. **Give the IME a truthful view of the text near the caret** (R2, R3). `MintedEditorView` exposes a small `IImeTextContext` (plain text of the caret's paragraph plus caret and selection offsets). `GetTextBeforeCursor/AfterCursor/SurroundingText/ExtractedText/SelectedText` answer from it. `SetComposingRegion(start,end)` adopts that slice as the current composition, so the following `SetComposingText` diffs correctly. Paragraph-scoped is enough: IMEs ask for at most a few hundred characters around the caret.
3. **Focus becomes first-class** (R1). Each platform capture view reports native focus gain and loss through a new `KeyboardProxy.FocusChanged` event. Android uses `OnFocusChanged`, iOS uses `BecomeFirstResponder`/`ResignFirstResponder` overrides, Windows uses `GotFocus`/`LostFocus`. `MintedEditorView` keeps `IsEditorFocused`, draws the caret only when focused, runs the blink timer only while focused (which also fixes the perpetual 100 ms repaint), and raises `EditorFocusChanged` from the real signal. The `Focus()`/`Unfocus()` methods stop raising the event themselves, which would otherwise fire twice.
4. **Grapheme-safe delete** (R7). Backspace/Delete step over a whole surrogate pair and use `StringInfo` text-element boundaries, so they never leave a lone surrogate.
5. Keep `TextFlagNoSuggestions`. Samsung ignores it anyway, and the composing path now copes either way.

**Out of scope:** drawing a composing-region underline, IME candidate-window positioning (`CursorAnchorInfo`), #2 (cursor zoom), a full document-wide shadow `Editable`. These are logged as follow-ups if wanted.

### Phase C: Grapheme-safe deletion (R7)

**C1.** `EditorInputController.HandleBackspace` / `HandleDelete`: compute the previous/next text-element boundary with `StringInfo.GetNextTextElementLength` (or `char.IsSurrogatePair`) against the block text instead of using `±1`.
- Tests (`TextInputTests`): backspace after `"a😀"` leaves `"a"`. Delete before `"👍🏽b"` leaves `"b"`. Backspace after `"é"` (decomposed `e`+U+0301) leaves `""`.
- Note: `ImeCompositionTracker` keeps working in UTF-16 units for its own diffs, but it must convert to grapheme-aware deletes. **Decision:** the sink takes a `DeleteBackwardChars(int utf16Units)` path that deletes an exact range, separate from user Backspace, so the composition diff never over-deletes.

## 8. Implementation notes (2026-10-20)

- Gboard on API 35 with `TextFlagNoSuggestions` delivers characters via `commitText`, not `setComposingText`; the composing path (Samsung/MIUI) is covered by unit tests only.
- Found during verification: once the connection reported real surrounding text, Gboard started offering suggestions from existing text, and picking one used `replaceText` (API 34+). `BaseInputConnection` applies that to its own private `Editable`, so the pick was silently lost. Fixed by overriding `ReplaceText` and `CommitCompletion` (`ImeCompositionTracker.Replace`).
- IME offsets are paragraph-relative. Enter, or Backspace/Delete that merges paragraphs, triggers `RestartInput` so the IME re-reads the new paragraph; other edits use `UpdateSelection`.
- Commits: `64ffc93` (Phase A), `090d53d` + `22862ca` (Phase B), `cada75b` (Phase C).
